## 1. Git ve GitHub Temel Kavramları

### Repository
Repository'yi projenin dosyalarını ve bütün değişiklik geçmişini tutan klasör olarak anladım. Benim bilgisayarımdaki local repo, GitHub'daki ise remote repo oluyor. Ben hiz_kontrol klasörüne girip git init yazarak ilk repomu oluşturdum.

### Stage
Stage, commit atmadan önce hangi değişiklikleri kaydedeceğimi seçtiğim ara alan. pid.py dosyasını oluşturunca git status yazdım ve dosyanın untracked göründüğünü gördüm. git add ile stage'e ekleyince commit'e hazır hale geldi.

### Commit
Commit'i stage'deki değişiklikleri bir mesajla kaydetmek olarak düşünüyorum. Her commit'in kendi kodu (hash) oluyor ve istediğim zaman o hale geri dönebiliyorum. Ben önce PID kodunun ilk halini commit ettim, sonra Kp değerini 1.0'dan 1.2'ye çıkarıp ikinci commit'imi attım.

### Branch
Branch, main'i bozmadan yeni bir şey denemek için açtığım ayrı bir çalışma dalı. Ben hız sınırlama fonksiyonu eklemek için hiz_limiti diye bir branch açtım ve değişikliği orada yaptım. main'e geri geçtiğimde o fonksiyonun dosyada olmadığını gördüm.

### Merge
Merge ile bir branch'teki değişiklikleri başka bir branch'e aktarıyorum. Ben hiz_limiti branch'ini main ile birleştirdim ve fonksiyon main'e de geldi. Bir de bilerek conflict çıkarmayı denedim: bir branch'te Kp'yi 0.8, diğerinde 1.5 yaptım. Birleştirirken Git hangisini alacağını bilemedi ve conflict verdi. Dosyayı açıp doğru değeri bıraktım ve tekrar commit ederek çözdüm.

### Push ve Pull
Push ile bilgisayarımdaki commit'leri GitHub'a gönderiyorum, pull ile de GitHub'daki yeni değişiklikleri bilgisayarıma çekiyorum. Önce projemi push ettim. Sonra projeyi başka bir klasöre de indirdim, orada bir dosya ekleyip push ettim. İlk klasöre dönüp pull yapınca o dosya bana geldi. Böylece başka biri değişiklik yaptığında pull ile ona nasıl ulaşacağımı görmüş oldum.

## 2. Takımlar Neden Git ve GitHub Kullanır?

Bence bir takımda birden fazla kişi aynı kod üzerinde çalıştığı için Git ve GitHub çok gerekli. Kodu tek bir yerde düzenli tutuyor, kimin neyi değiştirdiğini gösteriyor ve herkesin birbirini bozmadan çalışmasını sağlıyor.

### Versiyon kontrolüne neden ihtiyaç duyulur
Versiyon kontrolü olmadan kod_son, kod_son2, kod_gercek_son gibi dosyalar oluşuyor. Ben de daha önce bu şekilde çalıştım ve hangisinin güncel olduğunu karıştırdığım oldu. Kimin neyi neden değiştirdiği bilinmiyor, kod WhatsApp'tan ya da flash bellekle paylaşılınca birinin yaptığı iş üstüne yazılıp kaybolabiliyor. Bir şey bozulunca eski çalışan halin kopyası yoksa geri dönmek de mümkün olmuyor.

Commit geçmişinde her değişiklik tarihi, yapanı ve mesajıyla kayıtlı olduğu için bu sorunlar çözülüyor. Hatalı bir değişiklik yaparsam git revert ile o commit'i geri alabiliyorum ya da çalışan eski bir commit'e dönebiliyorum. Bunu da denedim: projemde bilerek dt yerine 0 yazdım, kod sıfıra bölme hatası verdi. Sonra git revert ile o commit'i geri aldım ve kod tekrar çalıştı.

### Git ile GitHub arasındaki fark
Başta ikisini aynı şey sanıyordum. Sonra öğrendim ki Git bilgisayarımda çalışan bir versiyon kontrol programı ve internet olmadan da kullanabiliyorum. GitHub ise Git repolarını internette tutan bir site, üstüne pull request ve issue gibi takım çalışması özellikleri ekliyor. Yani bana göre Git işin kendisi, GitHub da onu barındıran platform. Araştırdığım kadarıyla GitHub'ın alternatifleri GitLab, Bitbucket, Gitea ve Azure DevOps.

### Ekip çalışmasına katkıları
Herkes kendi branch'inde çalıştığı için kimse birbirinin kodunu bozmuyor. İşimi bitirince pull request açıyorum, yani "benim değişikliklerimi main'e alır mısınız" demiş oluyorum. Takımdan biri kodumu inceliyor (code review), gerekirse yorum yapıp düzeltme istiyor, onaylarsa main'e merge ediliyor.

Örnek olarak şöyle düşündüm: Ben hız kontrolü üzerinde, bir arkadaşım şerit takibi üzerinde ayrı branch'lerde çalışıyoruz. İkimiz de ayar dosyasındaki maksimum hız değerini farklı değiştirmişiz. Ben pull request açıp merge ettikten sonra arkadaşım merge etmeye çalışınca merge conflict çıkıyor. Konuşup hangi değerin doğru olduğuna karar veriyoruz ve conflict'i çözüyoruz.

### GitHub'ın proje yönetimi özellikleri
- Görev takibi: Issues ile görevleri ve hataları açıp kişilere atayabiliyoruz. Projects ile de bunları kanban panosunda (yapılacak, yapılıyor, bitti) takip edebiliyoruz.
- Dokümantasyon: README ile projenin ne olduğunu ve nasıl çalıştırıldığını anlatabiliyoruz. Daha uzun dokümanlar için Wiki var.
- Otomasyon: GitHub Actions ile her push'ta kodun derlenip derlenmediğini veya testlerin geçip geçmediğini otomatik kontrol edebiliyoruz.

Bence bizim takımda haftalık görevler issue olarak açılıp kişilere atanabilir ve panodan takip edilebilir. Kurulum ve kalibrasyon adımlarını Wiki'ye yazabiliriz. Actions ile de bozuk kodun main'e girmesini engelleyebiliriz.

### Kulüp ve takımlar için önemi
Öğrenci takımlarında üyeler mezun olunca kod genelde onların bilgisayarında kalıp kayboluyor. Bence bunu önlemek için kod kişisel hesaplarda değil, takımın GitHub hesabında tutulmalı. Her projenin README'si olmalı, commit mesajları anlaşılır yazılmalı, karşılaştığımız sorunlar ve çözümleri issue veya Wiki'de kayıtlı kalmalı.

Bu yeni gelenlere de çok yardımcı olur. Ben de takıma yeni katılan biri olarak bir repo bulsam README'den sistemi çalıştırabilir, commit geçmişinden ve eski issue'lardan neyin neden yapıldığını öğrenebilirdim. Sıfırdan başlamak zorunda kalmazdım.

### Otonom araç projesindeki yeri
Otonom araçta algılama, planlama, kontrol gibi birimler aynı yazılım üzerinde çalışıyor. Bence her birim kendi branch'inde paralel çalışıp işi bitince pull request ile main'e ekleyebilir. Böylece main hep araca yüklenebilecek, çalışan kod olarak kalır.

Saha testinde kullandığımız sürümü tag ile işaretleyebiliriz (mesela saha-testi-1). Böylece testte hangi kodu ve hangi parametreleri kullandığımız belli olur. Testte sorun çıkarsa çalıştığını bildiğimiz son sürüme hemen dönebiliriz. Kontrol tarafıyla ilgilendiğim için özellikle PID kazançları gibi parametrelerin de bu şekilde kayıt altında olmasını önemli buluyorum.

### Dikkat edilmesi gerekenler
- Şifre ve API key gibi bilgileri repoya yüklersem herkes görebilir, silsem bile geçmişte kalıyor. Bunları .gitignore ile repo dışında tutmam gerekiyor.
- Büyük dosyalar (veri setleri, kayıtlar) repoyu şişiriyor. Bunları repoya atmamalı ya da Git LFS kullanmalıyız.
- Doğrudan main'e push edersem test edilmemiş kod çalışan sürümü bozabilir. Bence main korumaya alınmalı ve her şey pull request ile eklenmeli.
- git push --force başkalarının commit'lerini silebilir. Ortak branch'lerde kullanmamak gerekiyor.
- "düzeltme", "son" gibi commit mesajları geçmişi anlaşılmaz yapıyor. Ben ne yaptığımı kısaca yazmaya dikkat ediyorum.
- Uzun süre pull yapmadan çalışırsam çok fazla conflict çıkıyor. Çalışmaya başlamadan ve push etmeden önce pull yapmalıyım.
- Conflict'i incelemeden "benimki doğru" diye çözersem arkadaşımın işi kaybolabilir. İlgili kişiyle konuşarak çözmek gerekiyor.
